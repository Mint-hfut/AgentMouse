# 微信防激活试验与人工点击故障

用户确认另一位负责隐藏桌面的 agent 已停下后，进行了一次绑定真实进程创建时间、PID 和 HWND 的试验。截图内容及账户信息未提交。

## 观察

- 微信原生主窗口当时隐藏。调用原有 `show_window` 后，获得了真实窗口图像。
- 单次排队点击拟从“QQ邮箱提醒”切换到“文件传输助手”，未发送聊天消息。
- 一秒期限的 CBT/subclass 保护记录 23 次激活阻断、23 次焦点阻断、0 次位置阻断。
- 采样期间前台变化；目标未越过原前台；鼠标坐标与系统输入时间在操作检查点未改变；结束时线程鼠标捕获为 0。
- 后续画面未显示会话切换。保护就绪查询在解除后为 false，两条外部 hook 撤下成功。
- 用户报告真实鼠标也不能操作微信。只读检查 `enabled=true`、`hung=false`、capture=0，不能据这些指标否定用户报告。
- 当前线程桌面和输入桌面均为 Default。后续曾读到空前台，再后续用户前台为 ZCode；这不是连续事件跟踪，不能据此断言所有变化的具体原因。
- 用户确认没有待保留内容并授权重启。仅重启已核对身份的原微信主进程；新实例未加载本轮 DLL。用户确认真实鼠标已恢复正常点击。

恢复过程中尝试正常启动入口未恢复原窗口，新增启动进程已单独停止；原实例的重启另经用户明确授权。没有发布该实验作为修复版。

## 确认的代码问题与修复

`ShowBackground` 直接用 `SetWindowPos(SWP_SHOWWINDOW)` 展开隐藏 Qt 窗口，会造成 Win32 可见而 Qt 的 QWidget 与子控件仍为隐藏状态。自建 Qt 5.15.2 已复现此不一致；通过 Qt 自身的 `show()` 可恢复一致。

这不是微信全部故障根因的证明：同一自建程序在状态不一致时，消息点击仍可以送达。因此不能声称“Qt 状态修复就一定解决微信卡死”。

修复共享原生 `show_window`：对于隐藏且窗口类以 Qt 开头的目标，在任何显示写入前返回 `application_restore_required`，保持原状。Core/Full 共用此入口。新增真实 Qt 回归同时验证拒绝操作、原生/框架状态不一致、框架自身恢复；原生窗口路由与 Full SDK 回归通过。

受限 pilot 也改为在采样到前台、层级或输入活动变化时停止等待并进入解除流程。该代码只保留为诊断源文件，不连接 MCP，尚未再次装入微信验证。

## 保留限制

早期人工点击失效发生在没有本轮 hook 的版本中；本轮又同时涉及隐藏窗口展开、截图、消息输入及 hook。未取得故障时线程调用栈/转储，也未分离每个变量，不能将所有卡死归因于某一个环节。

本轮实验 DLL 为避免卸载仍被引用的回调而保留模块引用。解除操作不等于卸载 DLL；本次经重启已清除。后续应在一次性应用进程里验证激活依赖和人工接管，不再把用户微信作为首次验证对象。
